# Amazon Aurora

[Amazon Aurora](https://aws.amazon.com/rds/aurora/)  is a MySQL and PostgreSQL-compatible relational database built for the cloud, that combines the performance and availability of traditional enterprise databases with the simplicity and cost-effectiveness of open source databases.

[

#### Tip #1: Auto-scale your read replicas

](#tip1)

You can use [Aurora Auto Scaling](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Integrating.AutoScaling.html)  to automatically add or remove Aurora Replicas in response to changes in performance metrics that you specify.

*   [Amazon Aurora supports Auto Scaling for Aurora Replicas](https://aws.amazon.com/about-aws/whats-new/2017/11/amazon-aurora-now-supports-auto-scaling-for-aurora-replicas/) 
*   [Amazon Aurora Auto Scaling with Aurora Replicas](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Aurora.Integrating.AutoScaling.html) 
*   [Building serverless applications with Amazon Aurora Serverless](https://aws.amazon.com/getting-started/hands-on/building-serverless-applications-with-amazon-aurora-serverless/) 

[

#### Tip #2: Consider dedicated readers for specific use cases

](#tip2)

You might be using your Amazon Aurora cluster for different access patterns or workloads at the same time such as both transactional applications and your report or BI. In such situations, it is likely that the most demanding workload condition the cluster sizing (ie. [DB instance classes](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/Concepts.DBInstanceClass.html)  such as `db.t3`, `db.r5`, etc.). This may force you to over provision your cluster even though the most demanding workload does not access the database 24/7. You are still paying for the full capacity.

In this particular case, it might be interesting to add a read replica dedicated to the intermittent workload needs - maybe on a certain schedule - and keep your DB Instance classes smaller.

[

#### Tip #3: Consider replacing read replicas used for OLAP or ML by Snapshot on Amazon S3

](#tip3)

You can export Amazon Aurora snapshots to [Amazon S3](https://aws.amazon.com/s3/)  as [Apache Parquet](https://parquet.apache.org/) . Parquet is an efficient open columnar storage format for analytics and is up to 2x faster to export and consumes up to 6x less storage in Amazon S3, compared to other text formats. You can analyze the exported data with other AWS services such as [Amazon Athena](https://aws.amazon.com/athena/) , [Amazon EMR](https://aws.amazon.com/emr/) , and [Amazon SageMaker](https://aws.amazon.com/sagemaker/) .

You'll find instructions on getting started on the [Aurora documentation](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_ExportSnapshot.html) .

[

#### Tip #4: Consider Reserved instances

](#tip4)

Using [reserved DB instances](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/USER_WorkingWithReservedDBInstances.html) , you can reserve a DB instance for a one- or three-year term. Reserved DB instances provide you with a significant discount compared to on-demand DB instance pricing. Reserved DB instances are not physical instances, but rather a billing discount applied to the use of certain on-demand DB instances in your account. Discounts for reserved DB instances are tied to instance type and AWS Region.

[

#### Tip #5: Consider switching to Amazon Aurora serverless

](#tip5)

Amazon Aurora Serverless is an on-demand, auto-scaling configuration for Amazon Aurora (MySQL-compatible and PostgreSQL-compatible editions), where the database will automatically start up, shut down, and scale capacity up or down based on your application's needs.

Use cases for [Amazon Aurora serverless](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless.html#aurora-serverless.use-cases) :

*   Infrequently Used Applications
*   New Applications
*   Variable Workloads
*   Unpredictable Workloads
*   Development and Staging Databases
*   Multi-tenant applications

**Trade-offs**:

*   You can also choose to pause your Aurora Serverless DB cluster after a given amount of time with no activity. When the DB cluster is paused, no compute or memory activity occurs, and you are charged only for storage. Resuming the database may add latency to the first incoming requests.
*   Aurora cloning, Aurora global database, Aurora Replicas, Performance Insights and other Aurora features are not available
*   See [Limitations](https://docs.aws.amazon.com/AmazonRDS/latest/AuroraUserGuide/aurora-serverless.html#aurora-serverless.limitations)  for a complete list.

Perform tests of your workload.

[

#### Tip #6: Increase your elasticity

](<#tip 6>)

Development and staging environments are typically only used for eight hours a day during the work week. You can stop these resources when they’re not in use resulting in a potential cost savings of 75% (40 hours versus 168 hours).

You can deploy the [AWS Instance Scheduler Solution](https://aws.amazon.com/solutions/implementations/instance-scheduler/) , create schedule based on business requirements and tag non-production EC2 and RDS instances to be scheduled.

![AWS Instance Scheduler](https://static.us-east-1.prod.workshops.aws/public/8844589c-f6be-4752-bd27-0dad323d1eb9/static/images/001_intro/002_core_activities/instance-scheduler.png?classes=shadow&width=500px)

This solution is [open source](https://github.com/awslabs/aws-instance-scheduler) , you can contribute to it or simply modify it to further suit it to your own requirements.

View the [implementation guide](https://docs.aws.amazon.com/solutions/latest/instance-scheduler/welcome.html)  for more details.
