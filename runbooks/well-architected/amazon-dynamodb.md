# Amazon DynamoDB

[Amazon DynamoDB](https://aws.amazon.com/dynamodb/)  is a key-value and document database that delivers single-digit millisecond performance at any scale. It's a fully managed, multi-region, multi-master, durable database with built-in security, backup and restore, and in-memory caching for internet-scale applications.

[

#### Tip #1: Switch to on-demand capacity model for new and unsteady workload (don’t over provision)

](#tip1)

Amazon DynamoDB [On-Demand Mode](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadWriteCapacityMode.html#HowItWorks.OnDemand)  is a flexible billing option for DynamoDB capable of serving thousands of requests per second without capacity planning. DynamoDB On-Demand Mode offers simple pay-per-request pricing for read and write requests so that you only pay for what you use, making it easy to balance costs and performance.

For tables using On-Demand Mode, DynamoDB instantly accommodates customers’ workloads as they ramp up or down to any previously observed traffic level. If the level of traffic hits a new peak, DynamoDB adapts rapidly to accommodate the workload.

[

##### Trade-offs

](#trade-offs)

*   As DynamoDB On-Demand Mode scales for you it will do so as requests increase. If you want to stay at or below a defined request rate and you know your workload requirements, use Provisioned Mode (see **Tip #2**).
*   On-Demand Mode always instantly accommodates up to double your previous peak traffic on a table to help ensure that your workload does not experience throttling. However, throttling can occur if you exceed double your previous peak within 30 minutes.

Be careful, you can only switch between read/write capacity modes once every 24 hours.

With Amazon DynamoDB [Provisioned Mode](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadWriteCapacityMode.html#HowItWorks.ProvisionedThroughput.Manual)  you specify the number of [data reads and writes per second](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/HowItWorks.ReadWriteCapacityMode.html#HowItWorks.ProvisionedThroughput.Manual)  that you require for your application. Consider using provisioned mode when your application traffic is predictable, consistent or ramps up gradually. Provisioned Mode enables your workload to run within a specified capacity, which gives you cost predictability.

Alternatively, you can use auto scaling (see **Tip #3**) to automatically adjust your table's capacity based on the specified utilization rate (upper and lower limits) to ensure application performance while reducing costs.

[

##### Trade-offs

](#trade-offs)

*   If you do not know about your table's capacity requirements, try On-Demand Mode (see **Tip #1**) to help you gauge your workload's demands and avoid potential throttling.

Be careful, you can only switch between read/write capacity modes once every 24 hours.

#### Tip #3: Enable auto-scaling to adjust provisioned capacity

](#tip3)

Many database workloads are cyclical in nature, for example day-time vs. night-time behavior might differ or your application is growing through rapid adoption and with that the requirements for your DynamoDB tables change. Demand for your application exceeding your available database resources translates in slow performance and poor user experience, as well as keeping unnecessary database capacity in low-times result in otherwise avoidable costs.

DynamoDB [Auto Scaling](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/AutoScaling.html)  dynamically adjusts provisioned throughput capacity in response to actual traffic patterns. Provisioned throughput settings are modified only when the actual workload stays elevated (or depressed) for a sustained period of several minutes. The Application Auto Scaling target tracking algorithm seeks to keep the target utilization at or near your chosen value over the long term.

You can manage DynamoDB Auto Scaling via the [AWS Console](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/AutoScaling.Console.html) , [AWS CLI](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/AutoScaling.CLI.html)  or the [AWS SDK](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/AutoScaling.HowTo.SDK.html) .

[

##### Trade-offs

](#trade-offs)

A decrease is allowed up to four times, anytime per day. A day is defined according to Universal Coordinated Time (UTC). Additionally, if there was no decrease in the past hour, an additional decrease is allowed. This effectively brings the maximum number of decreases in a day to 27 times (4 decreases in the first hour, and 1 decrease for each of the subsequent 1-hour windows in a day). More information [here](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Limits.html) .

When you work with Amazon DynamoDB, you might want to add flexibility to your queries as well as provide faster access to frequently queried items. [Global secondary indexes (GSI) and local secondary indexes (LSI)](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/SecondaryIndexes.html)  allow you to reshape the data in your DynamoDB tables to allow for exactly that.

In a fast moving environment you may have added LSI or GSI indexes that you no longer use. Since you [pay for those indexes](https://aws.amazon.com/dynamodb/pricing/) , consider deleting the unused indexes after monitoring their usage.

[

##### Trade-offs

](#trade-offs)

While GSI can be deleted at anytime, LSI can only be deleted with the table, which requires a migration to new table.

#### Tip #5: Remove SCAN operations from your code

](#tip5)

When

Difficulty

Implementation time

always, if feasible

300

hours to days

In general, [Scan](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Scan.html)  operations are less efficient than other operations in DynamoDB. A Scan operation always scans the entire table or secondary index. It then filters out values to provide the result you want, essentially adding the extra step of removing data from the result set. Additionally, as a table or index grows, the Scan operation slows. Since the Scan operation examines every item for the requested values it can use up the provisioned throughput for a large table or index in a single operation.

If possible, try to avoid using a Scan operation on a large table or index with a filter that removes many results. For faster response times, design your tables and indexes so that your applications can use [Query](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_Query.html)  instead of Scan. For example, a frequently queried attributes can be part of a secondary index for faster retrieval and supports queries. (For tables, you can also consider using the [GetItem](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_GetItem.html)  and [BatchGetItem](https://docs.aws.amazon.com/amazondynamodb/latest/APIReference/API_BatchGetItem.html)  APIs.)

Alternatively, design your application to use Scan operations in a way that minimizes the impact on your request rate.

#### Tip #7: Consider Using Batch Window to process your Streams with Lambda

](#tip7)

When

Difficulty

Implementation time

always, if feasible

300

hours to days

[DynamoDB Streams](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/Streams.html)  captures a time-ordered sequence of item-level modifications in a DynamoDB table. Applications can access those series of stream records from a DynamoDB stream in near real time. Also, the streams can be read with [AWS Lambda](https://aws.amazon.com/lambda/) .

AWS Lambda supports [Batch Windows](https://docs.aws.amazon.com/lambda/latest/dg/with-ddb.html) , a feature that allows developers to fine-tune Lambda invocation for cost optimization. This feature gives you additional control on batching behavior when processing data from DynamoDB streams (and Amazon Kinesis data streams).

Lambda reads records from a stream at a fixed cadence and invokes a function with a batch of records. With Batch Window, you can increase the average number of records passed to the function with each invocation. This is helpful when you want to reduce the number of invocations and optimize cost.

Batch Window allows you to wait as long as 300s to build a batch before invoking a function. A function is invoked when one of the following conditions is met:

*   the payload size reaches 6MB,
*   the Batch Window reaches its maximum value,
*   or the Batch Size reaches its maximum value.

[

##### Trade-offs

](#trade-offs)

*   Ultimately the requirements of your applications will dictate the Batch Window size:
    *   If it is sufficient to batch data over in bigger intervals than try to use bigger Batch Windows.
    *   Otherwise experiment with different Batch Window sizes to find the right trade-off between invocation time and costs.

#### Tip #8: Use AWS Managed Key instead of your own key if possible

](#tip8)

When

Difficulty

Implementation time

By default, all DynamoDB tables are [encrypted](https://docs.aws.amazon.com/amazondynamodb/latest/developerguide/EncryptionAtRest.html)  under an AWS owned customer master key (CMK) in the DynamoDB service account. However, you can select to encrypt some or all of your tables under a customer managed CMK or the AWS managed CMK for DynamoDB in your account instead.

The **AWS owned CMK is free of charge** and its use does not count against AWS KMS resource or request quotas and so does not incur additional charge. Customer managed CMKs and AWS managed CMKs charge for each API call and AWS KMS quotas apply to these CMKs.

You can switch the encryption keys with a single click in the AWS Management Console, a simple API call, or with the AWS Command Line Interface (CLI)

#### Tip #9: Consider storing larger items in S3 and include a reference token in a table item

](#tip-9:-consider-storing-larger-items-in-s3-and-include-a-reference-token-in-a-table-item)

When

Part of DynamoDB pricing is based on read capacity units (RCUs). For binary items such as images, it is usually more cost-efficient to use S3 for storage instead of storing it within DynamoDB. Instead, it is best practice to store larger items in S3 and include a reference token in a table item.

Many web developers who are new to serverless are familiar with using relational databases, so choose Amazon RDS for their database needs. Depending upon your use-case and data access patterns, it may be more cost effective to use DynamoDB instead. RDS is not a serverless service so there are monthly charges for the underlying compute instance. DynamoDB pricing is based upon usage and storage, so for many web apps may be a lower-cost choice.
