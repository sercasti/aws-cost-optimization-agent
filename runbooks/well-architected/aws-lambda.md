# AWS Lambda

[AWS Lambda](https://aws.amazon.com/lambda/)  lets you run code without provisioning or managing servers. You pay only for the compute time you consume.

With Lambda, you can run code for virtually any type of application or backend service - all with zero administration. Just upload your code and Lambda takes care of everything required to run and scale your code with high availability. You can set up your code to automatically trigger from other AWS services or call it directly from any web or mobile app.

[

#### Tip #1: Right size your memory

](#tip-1:-right-size-your-memory)

When

Difficulty

Implementation time

Always

200

1 hour

The amount of allocated RAM impacts the amount of CPU time and network bandwidth your function receives. Simply choosing the smallest (or the biggest) RAM amount to run your function is an anti pattern. With the biggest RAM, you might pay for unnecessary resources. With the smallest RAM, your function might run longer and cost you more.

Right sizing can be done using AWS Compute Optimizer or AWS Lambda Power Tuning.

AWS Compute Optimizer [helps you](https://aws.amazon.com/blogs/compute/optimizing-aws-lambda-cost-and-performance-using-aws-compute-optimizer/)  optimize two categories of Lambda functions. The first category includes Lambda functions that may be overprovisioned in memory sizes. You may consider downsizing the memory sizes of these functions to save costs. The second category includes compute-intensive Lambda functions that may benefit from additional CPU power. You may consider increasing their memory sizes to trigger an equivalent increase in CPU available to these functions and reduce runtime. For functions that do not fall under any of these categories, Compute Optimizer does not deliver recommendations for them. AWS Compute Optimizer analyzes 14 days of Lambda function invocation history, including function runtime duration, CPU time used, and memory usage, to deliver recommendations.

[AWS Lambda Power Tuning](https://github.com/alexcasalboni/aws-lambda-power-tuning)  is a state machine powered by AWS Step Functions that helps you optimize your Lambda functions in a data-driven way. The state machine is designed to be easy to deploy and fast to execute. Also, it's language agnostic so you can optimize any Lambda functions in your account. In short, you provide a Lambda function ARN as input and the state machine invokes that function with multiple configurations (from 128MB to 10GB, you decide). Then it analyzes all the execution logs and suggest you the best configuration that matched the given strategy objective: cost, performance or balanced. You have several [ways to deploy it](https://github.com/alexcasalboni/aws-lambda-power-tuning/blob/master/README-DEPLOY.md)  including a [CDK pattern](https://github.com/cdk-patterns/serverless)  or the use of the [`lumigo-cli`](https://www.npmjs.com/package/lumigo-cli#lumigo-cli-powertune-lambda) .

#### Tip #3: Watch your timeouts

](#tip-3:-watch-your-timeouts)

When

Difficulty

Implementation time

Always

400

Hours

If your function times out it basically means you pay for unfinished processing (which probably must be executed again).

If your AWS Lambda application is working perfectly fine, it doesn't mean that your AWS Lambda function doesn't unnecessarily time out.

This may happen with Node.js because of the [`callbackWaitsForEmptyEventLoop`](https://docs.aws.amazon.com/lambda/latest/dg/nodejs-context.html)  AWS Lambda context object default behavior.

AWS Lambda doesn't provide a timeout metric, to look for timeouts:

*   You can look at CloudWatch metrics for your AWS Lambda function. If the **Duration** graph presents a flat line, it means that there is timeout.
*   You can [create your own metrics from Log Events using filters](https://docs.aws.amazon.com/AmazonCloudWatch/latest/logs/MonitoringLogData.html) . Use the **filter pattern** `Task timed out after` against a particular AWS Lambda function’s log group.

You can refer to the following blog post for a deep dive on the topic [Debugging AWS Lambda Timeouts](https://lumigo.io/blog/debugging-aws-lambda-timeouts/)  - written by one of our AWS Serverless heroes [Yan Cui](https://aws.amazon.com/developer/community/heroes/yan-cui)  published by Lumigo, an AWS partner.

#### Tip #4: Choose the most appropriate runtime

](#tip-4:-choose-the-most-appropriate-runtime)

When

Difficulty

Implementation time

400

\-

Based on the language you choose, the execution time may change which translates into different costs (as the lambda pricing model is based on the execution time).

*   Prefer languages like Node.js or Python over languages like Java and C# if cold start time is affecting user experience. You'll find extensive comparison [here](https://theburningmonk.com/2017/03/aws-lambda-comparing-platform-performances/) , [here](https://medium.com/the-theam-journey/benchmarking-aws-lambda-runtimes-in-2019-part-i-b1ee459a293d)  or [here](https://medium.com/the-theam-journey/benchmarking-aws-lambda-runtimes-in-2019-part-ii-50e796d3d11b) .
*   Behaviors for subsequent requests might differ (see previous posts for more details).
*   If you want predictable startup times, look at [Provisioned Concurrency](https://aws.amazon.com/blogs/compute/new-for-aws-lambda-predictable-start-up-times-with-provisioned-concurrency/) .

You will find an exhaustive list of runtimes in the [documentation](https://docs.aws.amazon.com/lambda/latest/dg/lambda-runtimes.html) . You can also bring your [own runtime](https://docs.aws.amazon.com/lambda/latest/dg/runtimes-custom.html)  or use one of the runtime available in the [AWS Serverless Application Repository](https://serverlessrepo.aws.amazon.com/applications) 

If you go Java

*   You can use [Lambda SnapStart](https://docs.aws.amazon.com/lambda/latest/dg/snapstart.html) . Lambda SnapStart for Java can improve startup performance for latency-sensitive applications by up to 10x at no extra cost, typically with no changes to your function code. With SnapStart, Lambda initializes your function when you publish a function version. Lambda takes a Firecracker microVM snapshot of the memory and disk state of the initialized execution environment, encrypts the snapshot, and caches it for low-latency access. When you invoke the function version for the first time, and as the invocations scale up, Lambda resumes new execution environments from the cached snapshot instead of initializing them from scratch, improving startup latency.
*   You can use [Provisioned Concurrency](https://aws.amazon.com/blogs/compute/new-for-aws-lambda-predictable-start-up-times-with-provisioned-concurrency/)  to address the cold start time issue.
*   Use simpler IoC dependency injections like Dagger rather than Spring-Framework.

If you go Node.js

You can use minification to reduce the size of the package. This will reduce the time it takes to download the package significantly. In some cases, package size may reduce from 10MB to 1MB.

#### Tip #5: Remove unnecessary dependencies

](#tip-5:-remove-unnecessary-dependencies)

When

Difficulty

Implementation time

Always

400

Hours

When you initialize objects and dependencies in your AWS Lambda function, this increases the first execution time and the required memory of your AWS Lambda function. As you pay per duration and memory size, too big or unnecessary dependencies will increase your running cost.

You must be very careful about your deployment package contains. Include only what you need, optimize defaults and exclude what you're not explicitly using.

*   Use X-Ray to measure Lambda Initialization and Code Execution time
*   Use the URL Connection client instead of the Netty Http client from the v2 AWS SDK
*   List all the packages, check the number of classes/dependencies used and remove those that aren't needed
*   Check the dependency framework if you are using one
*   Limit the re-initialization of variables/objects on every invocation by using static class members instead
*   Don't use Interfaces or Abstract classes unless you really need to extend them

**Should I use a Dependency Injection framework?**

Concurrent Lambda invocations run in separate execution contexts, eliminating concurrency issues - singletons don't need to be handled, for example. While DI reduces boilerplate code (along with other benefits), the Lambda function's lifespan is relative to the task it is carrying out. In most cases, the startup cost imposed by common DI frameworks aren't immediately helpful given the AWS Lambda programming model. But if you really, really need a DI framework, look for one that loads quickly.

**What's your advice on Injection Frameworks?**

`Guice` uses reflection, so will slow down class loading. It should be avoided.

`Dagger` uses compiled code, so it's faster.

The `Spring framework` brings unnecessary complexity and features that won't be used in Lambda

#### Tip #8: Use short timeouts

When

Difficulty

Implementation time

Always

200

Sometimes an unexpected issue may result in a duration increase for your Lambda function. This can occur due a variety of reasons such as a network issue or an unusually high API response time. The longer the duration, the higher the cost. The function timeout will prevent the cost from increasing to extreme levels.

To choose a short timeout value, use CloudWatch to monitor your function's maximum [duration metric](https://docs.aws.amazon.com/lambda/latest/dg/monitoring-metrics.html)  under normal operation and choose a timeout value that is slightly higher.

[

##### Trade-offs

](#trade-offs)

Using a timeout value that is too short may result in unwanted timeouts under normal operation. Watch your timeouts as suggested in tip #3 and increase the timeout value if necessary.
